# Release notes for pkpdutils 1.5.0

Minor release of `pkpdutils` which sends the non-compartmental analysis, the summary statistics and the time to steady state to the rust kernel [`pkpdutils-core`](https://pypi.org/project/pkpdutils-core/) when it is installed and eligible, keeping the validated python implementation as the fallback and as the other side of a differential comparison (#128, #132, #133). The fixed cost of a call drops to about a third (#134) and three defects of the python analysis are fixed, one of which changed its answers (#129, #130, #131).

The kernel is a dependency with a floor and a cap, `pkpdutils-core>=0.4.1,<0.5`. Results agree between the two engines within `1e-6` relative, which a gate over the whole test suite asserts; where they cannot agree, the difference is documented on both sides.

## Breaking changes

- `time_to_steady_state` returns `NaN` for a monoexponential fit whose optimum is unbounded, which is what its own docstring always promised. It previously returned a finite number for a flat, a falling or a still linear series of troughs, and that number moved by twelve orders of magnitude with the starting values of the optimizer, so it was not reproducible between runs of the same data (#133).
- `Timecourses.ds` is read-only. A batch is its dataset, and the layout and the units are read from it once, so the dataset is fixed for the life of the batch. Build another batch around the dataset you want: `Timecourses(batch.ds.assign_coords(arm=("individual", arms)))`, which is what `select`, `groupby`, `mean`, `relative_to_dose` and `dose_normalized` already return (#134).

## The rust kernel

- `nca()` sends an eligible batch to `pkpdutils-core` and falls back to the python core for anything the kernel refuses, which the kernel itself decides rather than a restatement of its rules in the host (#128). Multiple dosing with its intervals and the steady state analysis followed (#132), then `ParameterResult.summarize` with its t interval and both time to steady state estimators, the monoexponential approach to the plateau and the stepwise linear trend test (#133).
- `PKPDUTILS_COMPARE_ENGINES=1` runs both engines on every batch which reaches the kernel on the non-compartmental path and compares the results at `1e-6` relative and `1e-12` absolute. The comparison covers that path alone, not `summarize` and not the time to steady state, which rest on their own tests (#133).
- The median of a summary goes through the same percentile as the kernel, so the two agree bit for bit rather than within an ulp (#133).
- One difference between the engines remains and is documented in both: on a series of troughs already saturated to the resolution of a double, the python search reports `NaN` where the kernel still recovers the rate (#133).

## Performance

- The fixed cost of a call falls by about two thirds (#134). One `nca()` call on twelve subjects of twenty-four points goes from 2.84 ms to 0.96 ms, and the share of it spent in the kernel rises from 2 % to 6 %, which is the point: the overhead of the dispatch was deciding where the kernel became faster than python, not the numerics.
- The layout and the units of a batch are read once instead of about ninety times per call, a result reads its stored variables instead of building a `DataArray` for each of about fifty, and the arrays are permuted with numpy rather than through `DataArray.transpose`. A pint quantity, a sparse or a chunked array still goes through xarray's own conversion.

## Fixes

- A batch of a single time point no longer raises in the back extrapolation (#129).
- The trough regression of the time to steady state is fitted about the centroid, so it is conditioned at large times (#130).
- The standard error of an exact terminal fit is zero on every platform, where it was a denormal or a small positive number depending on the compiler of the host (#131).
